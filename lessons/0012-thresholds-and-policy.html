Lesson 0012 · Homework 1, Problem 1

Thresholds and policy

A fitted score becomes a real action only once someone picks a cutoff. This lesson builds the skill with a library-alerts example — a different dataset from Homework 1's — so you can bring the same moves to the actual problem.

The pipeline, filled in

Homework 1, Problem 1(a) asks you to write the deployed pipeline as xi → si → ai. That's exactly Lesson 0001's deployment half, with names attached:

xi --f^D--> si --δt--> ai

xi: one student's features. f^D: the fitted model — produces si, a probability. δt: "flag if si ≥ t" — the decision rule. ai: contact the student, or don't.

The question underneath — "if the university changes t without retraining, what changes and what remains fixed?" — is the same "which one moved?" test from Lesson 0001. Changing t only touches δ. It never touches A, D, or f^D — the scores si themselves are identical before and after. What changes is which students end up on which side of the cutoff.

Confusion matrix at a threshold

Here's a parallel setup: a library sends a reminder call to any patron whose "will return this book late" score is at least t. Drag the threshold and watch the confusion matrix and TPR/FPR update live.

Notice what a lower threshold buys and costs: drag from t = 0.50 down toward t = 0.30. TPR goes up (fewer late-returners slip through uncalled) but so does FPR (more on-time patrons get an unnecessary call). There's no free lunch here — the tradeoff is baked into the ranking the model already produced; the threshold just decides where to cut it.

For Homework 1(b) and (c): build the same table by hand for t = 0.50 and t = 0.30 using the homework's own 8 scores and labels. Count TP/FP/FN/TN directly from the table — don't estimate off a chart. Then state the tradeoff in words: what's the practical benefit of the lower threshold, and what's the practical cost?

A capacity constraint is a second, independent decision

Homework 1(c) adds a wrinkle: the advising office can only contact four students a week. This is a different kind of constraint than the threshold — it doesn't come from the model or from TPR/FPR at all. It comes from downstream capacity.

The general lesson: a decision rule can depend on more than the score. "Flag if s ≥ t" is the simplest δ, but δ can also say "flag if s ≥ t, then act on at most k, ranked by s" — still a function of the score, still leaves f^D untouched, but now shaped by a real-world resource limit instead of a probability cutoff alone.

Why a random row split can lie to you

Homework 1(d) is about validation design, not thresholds — but it's testing the same instinct: does this procedure represent the situation you'll actually deploy into? Here, the twist is that the training data has multiple rows per student (weekly records), and the model will be deployed on students it has never seen a single row of before.

Random row split

Some of student A's weekly rows land in training, others in the held-out set. The model can partly "recognize" student A's own pattern — that's information it will never have for a genuinely new student.

Grouped (by-student) split

Every row for a given student goes entirely into training or entirely into the held-out set — never split across both. The held-out students are ones the model has literally never seen, which is exactly next year's entering class.

This is the same idea as Lesson 0001's D → A → f^_D: the held-out evaluation is only honest if it mimics the real deployment gap. A random-row split quietly leaks a bit of "I've seen this exact person before" into the evaluation, which can make accuracy look better on paper than it will look on a genuinely new student next fall.
